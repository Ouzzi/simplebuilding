# Plan b-lib01 (03.11.): Sub-Mods aus modules.json (B1) + Enderit-Regel aus einer Quelle (B3)

Basis 4388b8015 (Bündel 99). Hintergrund: /root/sb-tools-b/PLAN-ZEIT-2026-11-03.md (B1+B3 freigegeben). Ziel: weniger
Handarbeit und Merge-Konflikte beim Anlegen/Verschieben von Sub-Mods, Verhalten gleich.

## Ist-Stand (Arrows-/Enchanting-Merge)
Ein neuer Pflicht-Sub-Mod von SB brauchte Handeinträge in:
1. `mc26_3/fabric/build.gradle`: Ersetz-Zeile `"cloth-config": ">=26.3", "simplelib": ">=0.4.0", ...` (depends),
   je eine `.replace('"<id>": "*",', '')`-Zeile (suggests raus), `implementation project(...)`, `include project(...)`.
2. `src/main/resources/fabric.mod.json` suggests (`"<id>": "*"`).
3. `integration/enabled-mods.json` (Dev-Auswahl).
4. `ConfigOptions.RESTART_REQUIRED`, `SimplebuildingConfig` (Feld + `setSubMod`), `ConfigOptionTests` (EXPECTED_OPTIONS + switches).
5. Lang EN/DE (Name + Tooltip des Schalters), `docs/MODSTRUKTUR` (modtree, schon aus modules.json generiert).
Vorhanden: `modules.json` mit `requires`/`optional` von SB (Reihenfolge), `bundle`/`parent` je Sub-Mod, `modId`-Alias
(simpledimensions → simpledimension), `multimod.py` (prüft Nesting), `jsonreg3.py` (mergt modules.json je id/Wert),
`newmod.py` (Gerüst + enabled-mods), `moduleRegistry` in build.gradle/settings.gradle.

## Umsetzung
B1
- `mc26_3/fabric/build.gradle` liest `modules/modules.json`: Pflicht-Sub-Mods = SB.`requires` ∩ Module,
  optionale = SB.`optional` ∩ Module. Daraus: depends-Ersetzung (`">=<version>"`, Mod-Id-Alias), suggests-Entfernung je
  Pflicht-Sub-Mod, `implementation` = Pflicht + SB.`fabricDevClasspath` (neu: simplemaps, simplequestionary, simpletrims),
  `include` = Pflicht + optional. Handlisten entfallen.
- Neues Feld je Sub-Mod mit `parent: simplebuilding`: `"configSwitch"`: `true` (generierter Schalter `enableSimple<X>`),
  `"host"` (Feld von Hand, Mod liest den Schlüssel selbst: Maps, Questionary), `false` (kein Schalter: Ovens, Mobheads).
- `tools/submods/sync.py` schreibt zwischen `// <submods:begin NAME>` / `// <submods:end NAME>`:
  SimplebuildingConfig (fields, apply), ConfigOptions (restart), ConfigOptionTests (expected, switches); prüft außerdem
  suggests in fabric.mod.json (jeder optionale Sub-Mod; schreibt fehlende), Lang-Schlüssel EN/DE (nur Prüfung, Texte
  von Hand) und dass jeder SB-Sub-Mod `configSwitch` hat. `--check` = nur prüfen, Exit 1. Eingehängt als
  `checkSubMods` in die Check-Map von build.gradle (precheck findet ihn).
- enabled-mods.json bleibt Nutzer-Auswahl (Zentrale/Launchhub schreiben sie); newmod.py trägt neue Module schon ein,
  jsonreg3 mergt sie. Nicht generiert (Entscheidung: sonst würde sync abgewählte Mods wieder einschalten).
- Reihenfolge = modules.json. Abweichung: die Schalter im Reiter "Simple Mods" stehen danach in modules.json-Reihenfolge
  (Anzeige-Reihenfolge; Schlüssel, Defaults, Verhalten gleich, Gson liest nach Namen). Maps/Questionary bleiben oben.
- Merge zweier Sub-Mod-Branches: modules.json per jsonreg3, dann `python3 tools/submods/sync.py` überschreibt die
  Blöcke (auch mit Konfliktmarkern darin).
- Doku: AGENTS.md "Neuer Sub-Mod in 3 Schritten".

B3
- `ModTags.Items.ENDERITE_NAMESPACES` (shared, ohne Set.of-Duplikatfehler auf 26.2, wo alle Namespaces simplebuilding
  sind) = SB, MATERIAL, OVENS, CRUCIBLES, HAMMERS, STORAGE, ORES, PISTONS. `isEnderiteItemByRule` und beide Tests
  (void-protected 1b, everyEnderiteItem…) lesen nur diese Menge. Die Pfad-Regel bleibt im Test 1b bewusst zweimal
  formuliert (Absicht des Tests). Das Literal `"simplemachines"` der Tests = PISTONS_NAMESPACE auf 26.3, auf 26.2 ohne
  Items → Ergebnis gleich; Tag-Datei unverändert (Regel identisch, kein Datagen nötig).

## Risiken
- Reihenfolge der `implementation`-Abhängigkeiten ändert sich (Classpath-Reihenfolge der Dev-/Testläufe); Sub-Mods sind
  unabhängig, Tests zeigen es.
- Gradle-Ersetzung muss byte-gleiches Ergebnis wie vorher liefern: per Python-Simulation alt/neu vergleichen
  (fabric.mod.json nach Filter als JSON gleich).
