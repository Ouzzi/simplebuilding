Basis `hub/b-bundle194`. Antwortcode der Vorschau: **CONV51** (`/root/sb-tools-b/previews/b-conv51-preview.html`).
Phase 1 = dieses Konzept, ein klickbarer Prototyp je Seite, Tests. Kein Komplettbau, nichts öffentlich, keine Gradle-Läufe.

## 1. Ist-Stand (aus dem Quelltext)

**Blaupausen-Code (Simple Building Tools)** ist *Text*, kein Binär-/Base64-String: die „Bausprache“ (`BlueprintCode`,
Spezifikation `docs/BLUEPRINT.md`). Ein Bauwerk liegt im Raster 256³, x Ost, y oben, z Süd.
- Serialisierer `BlueprintCode.serialize(model)`: Kopfzeile `# BxHxT, N blocks`; je Blockzustand eine Anweisung, häufigste
  Zustände zuerst (Gleichstand: `spec` lexikographisch, Java-`String`-Ordnung); `spec` = Id ohne `minecraft:`, nur Eigenschaften
  abseits des Block-Standards (`name[a=b,c=d]`, Reihenfolge = `state.getProperties()`, also alphabetisch); Stellen gierig zu
  Quadern (Reihe in x, dann so weit wie möglich in z, dann Schichten in y; Stellen in Reihenfolge y, z, x); Achsenform
  `0..4,0,0..4`; Zeilenumbruch bei 100 Zeichen (derselbe Block beginnt die nächste Zeile); Zustand > 12 Zeichen, der mehr als
  eine Zeile braucht, bekommt Alias `$a`, `$b` … (`aliasName`: a..z, aa..).
- Scan beginnt an der kleinsten belegten Stelle (`normalized()`); Luft und `moving_piston` entfallen; Block-Entities: nur der
  Zustand, kein Inhalt; keine Entities.
- Grenzen: Raster 256 je Achse (`coordinate_range`); belegte Stellen ≤ 4 194 304; Wiederholung 1..256; **Codelänge beim
  Tippen/Einfügen/Editor 32 000** (`MAX_CODE_LENGTH`, c2s-Paket), gespeichert/gescannt bis 1 000 000 (nur Server-Scan, im Editor
  schreibgeschützt, FIX13B); Import-Dialog `BlueprintFormats.MAX_IMPORT_CHARS` 262 144. Baustab-Stufen nach längster Kante:
  16/32/48/64/128/256 (Kupfer … Enderit, `BlueprintTiers`). Kreativ-Blaupause: keine Volumengrenze, setzt auch Blöcke ohne Item.
- Vorhanden: Import/Export als Text in zwei Formaten (Bau-Code, Vanilla-`setblock`/`fill`-Liste, N55 `BlueprintFormats`).
  **Folge für N51:** Web-Codes über 32 000 Zeichen lassen sich nicht einfügen → der Konverter muss in Teile schneiden.
- Es gibt **keinen** Datei-Import (.nbt/.schem) in der Mod; N51 ist der erste.

**Modell-Code (Simple Models)**: kein eigenes Format. „Code“ = Vanilla-26.3-Modell-JSON, so wie der Editor es zeigt
(`ModelJson.writeCompact`, Code-Ansicht F4). Felder und Reihenfolge: `parent`, `ambientocclusion`, `gui_light`, `textures`,
`elements` (`name`, `from`, `to`, `rotation{origin,axis+angle | x,y,z, rescale}`, `shade_direction_override`, `light_emission`,
`faces{down,up,north,south,west,east: uv, texture, rotation, cullface, tintindex}`), `display`. Standardwerte entfallen.
Zahlen: ganze ohne `.0`, sonst kürzester Float32-Text. Kompaktlayout: Objekt/Array in eine Zeile, wenn es in 64 Zeichen passt.
Grenzen: from/to −16..32, ≤ 256 Elemente, ≤ 64 Texturen, ≤ 65 536 Zeichen, Tiefe 16, Licht 0..15, Flächendrehung 0/90/180/270,
Translation ±80, Skalierung ±4. Texturen sind Ressourcen-Ids (`mymodels:block/x`), Bilder kommen nicht mit.

**Wiki**: `wiki/index.html` ist eine statische Einzeldatei (offline lauffähig, `generate.py` → `data/*.js`), Dev-Bereich über
`isDevSite()` (Pfad `/dev/`, Dev-Overlay oder `?dev=1`). Es gibt keine Fremd-CDNs im Wiki (Pixeleditor: eigener Code in
`assets/`). Daher: keine Bibliothek nötig, siehe Formatwahl.

## 2. Formate und Entscheidung

| Format | Aufbau | Phase | Begründung |
|---|---|---|---|
| Vanilla `.nbt` (gzip) | Compound `DataVersion`, `size`, `palette` (`Name`, `Properties`), `blocks` (`pos`,`state`,`nbt`), `entities`; auch `palettes`; Create-Schematics gleich | **2, zuerst** (Prototyp) | einfachstes, verbreitetstes, Create nutzt es; Zustände stehen als Text, kein DataFixer für Zuordnung nötig |
| Sponge `.schem` v2/v3 | gzip-NBT; `Version`, `DataVersion`, `Width/Height/Length`, `Offset`, `Palette` (Text `id[props]` → Index), `BlockData` (VarInt-Bytes, Index `(y*Length+z)*Width+x`), `BlockEntities`; v3 kapselt in `Schematic` und `Blocks.{Palette,Data,BlockEntities}` | **2** | WorldEdit/FAWE/Axiom exportieren das; Palette ist Text → direkt `spec` |
| Sponge v1 | wie v2 ohne DataVersion | 2 (billig) | gleicher Leser |
| MCEdit `.schematic` | gzip-NBT `Blocks` (Byte), `Data`, `AddBlocks`, `Materials: Alpha`, `Width/Height/Length` | **2, optional** | nur numerische Alt-IDs + Meta: braucht eine Id-Tabelle (1.12) → Näherung mit Hinweis „unbekannt“ |
| Litematica `.litematic` | gzip-NBT, `Regions{name: {Position, Size (kann negativ), BlockStatePalette, BlockStates (gepackte Long-Array, Bits je Zustand = max(2, ceil(log2 Palette)), die Werte laufen über Long-Grenzen)}}`, `MinecraftDataVersion` | **2** | verbreitet bei Bauern; mehrere Regionen → Auswahl/zusammenführen |
| Axiom `.bp` | eigenes Binär (Magic `0x0AE5BB36`, Header + gzip-NBT mit Blöcken in Chunk-Sektionen); nur teildokumentiert | **zurückgestellt** | Layout nicht verlässlich belegt; Besitzerfrage, ob Bedarf (Anwender können Axiom als `.schem` exportieren) |
| Blockbench `.bbmodel` | JSON: `meta`, `resolution`, `elements` (cube: `from`,`to`,`origin`,`rotation`,`faces{uv,texture}`), `textures` (eingebettetes PNG, Base64), `outliner`, `display` | **2** (Prototyp) | Pixelmaße wie Vanilla → nahezu 1:1; fremde Gruppen/Animationen entfallen (Hinweis) |
| Vanilla-JSON-Modell | s. o. | **2** (Prototyp) | ist schon das Code-Format; Normalisierung + Prüfung gegen die Editor-Grenzen |
| `.obj` / `.gltf` / `.glb` | Dreiecksnetze | **2, ja/nein per CONV51** | kein Würfelmodell: nur Voxel-Näherung (Raster ≤ 32 → Würfel, Greedy-Meshing zu Quadern, ≤ 256 Elemente), klar als Näherung gekennzeichnet; glTF/GLB per JSON+Binär-Leser ohne Bibliothek |

**Technik**: reines JS ohne Bibliothek. gzip über `DecompressionStream('gzip')` (alle aktuellen Browser), eigener NBT-Leser/-Schreiber
(~60 Zeilen), VarInt/Long-Pack-Leser in eigenem Code. Vorschau: Canvas (Schichten bzw. gedrehte Projektion). Keine CDN-Bibliothek
(three.js nur auf Wunsch, Frage 2). Kein Server-Upload; Datei wird nur im Speicher gelesen.

## 3. DataVersion- und Block-State-Umrechnung

- Zustände in `.nbt`/`.schem`/`.litematic` stehen als Text (`Name` + `Properties` bzw. `id[k=v]`) → direkt `spec` (Standardwerte
  entfallen). Umrechnung nötig, wenn `DataVersion` deutlich älter als die Mod (26.3 ≈ 4440+) ist: Umbenennungen (z. B. 1.13
  „Flattening“-Ids, `grass_path` → `dirt_path`, Block-Umbenennungen 1.19–1.21). Plan: kompakte, nach DataVersion gestaffelte
  Umbenennungstabelle `renames.json` (Id- und Eigenschaftsumbenennungen), erzeugt aus den Vanilla-Datenfixern; Blöcke ohne
  Treffer in der Mod-Registry werden **markiert** (rot in der Vorschau, Liste, wahlweise zu Luft/Ersatzblock), nicht stillschweigend geändert.
- **Standardwerte** der Block-Eigenschaften (für das Weglassen) braucht die Seite vollständig: Prototyp enthält Regeln für die
  gängigen Familien (Treppe, Stufe, Zaun, Mauer, Tür, Falltür, Stamm, Laub, Glasscheibe, Leiter, Truhe, Ofen, Schild, Knopf, Bett);
  unbekannte Standardwerte → Eigenschaft wird mitgeschrieben (gültig, nur länger, Hinweis in der UI).
  Phase 2: `blockstates.json` (alle Blöcke der Mod-Stände, je Block Eigenschaften + Standardwerte) aus der Registry per Gametest/
  Datagen-Dump erzeugen (läuft auf sb-test) und im Wiki ausliefern; Test: Block-Liste = Registry.
- Mod-Blöcke (`simplebuilding:*`) behalten den Namensraum; aus anderen Mods stammende gelten als unbekannt, wenn sie nicht in `blockstates.json` stehen.
- Block-Entities: nur Zustand (wie der Scan). Hinweis mit Anzahl. Entities: ignoriert, Anzahl gemeldet.
- `structure_void` wird übersprungen (Vanilla-Konvention „nichts setzen“), `jigsaw` bleibt ein Block.

## 4. Grenzen, die die Seite anzeigt

Größe (B x H x T) und benötigter Baustab (16 … 256), Blockanzahl und Blockarten, Codelänge gegen 32 000; > 256 je Achse →
Phase 2 Kacheln (Prototyp: Hinweis); Code > 32 000 → **Teile von unten nach oben** (Prototyp umgesetzt, je Teil eigener
Kopf mit Versatz `# part i/n, place at +x,y,z`); Kreativ-Blaupause nötig für Blöcke ohne Item (aus Item-Liste, Phase 2);
Modelle: Elemente ≤ 256, Texturen ≤ 64, Ausdehnung −16..32, 65 536 Zeichen.

## 5. Rückweg Code → Datei

- Bauwerke: Bau-Code parsen (Parser der Bausprache nach JS portieren: Regionen, Alias, Variablen, Formen – groß, ~1 000 Zeilen;
  Prototyp: nur Achsenform für Tests) → `.nbt` (gzip, `DataVersion` der Mod) und `.schem` v3. Test: Datei → Code → Datei = gleiche Zellen.
- Modelle: Code (JSON) → `.json` direkt; → `.bbmodel` (Elemente, Texturnamen als leere Slots, `display`). Test: Rundlauf.
- Frage 5 (CONV51): Pflicht in Phase 2 oder später.

## 11. Risiken / Abweichungen

- Bit-Genauigkeit hängt an der Standardwert-Tabelle (siehe 3); mit Teil-Tabelle bleibt der Code gültig (parst zu demselben Modell), ist aber nicht byte-gleich zur Java-Ausgabe, wenn eine Eigenschaft mit unbekanntem Standard mitgeschrieben wird. Java-Testvektoren (Phase 2) schließen das.
- Prototyp nicht im Browser klickgetestet (kein Browser im CT, kein sbt/Gradle); getestet nur der Kern mit node.
- Formatdetails zu `.litematic`/`.bp` aus dem Gedächtnis, in Phase 2 gegen Beispieldateien zu verifizieren.
