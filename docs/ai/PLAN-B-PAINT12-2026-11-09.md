## Umsetzung
1. Generator neu: Bauteile (Enderman, Shulker, Chorus orthogonal, Insel, Stadtturm, Drache seitlich/frontal, Endkristall, Obsidiansäule, Portalrahmen, Enderauge, Perle, Ei, Endstab, Elytren …), 1-px-Rahmen wie Vanilla, flacher Himmel mit Bayer-Kante, feste Sterne.
2. Je Motiv eigene Szene (46 verschiedene, Titel teils angepasst: hollow = „Trophäe“, blink = „Endermilbe“) und 3 benannte Animationen. Phasenmodell: `draw(c, rng, P)`, `P[name] = t`; t = 0 ist für alle drei Animationen dasselbe Standbild (Start-Frame).
3. Datenformat: Frames `<id>_1..12` (Animation k = Frames 4k+1..4k+4), Abspielfolge bleibt ping-pong (alle Animationen hin-und-zurück entworfen). `EndPaintings.ANIM_COUNT = 3`; `EndPaintingAnim` lost bei jedem Start eine Animation aus (Timer speichert {Start, Animation}).
4. Tests: Timer-Test erweitert (Animation 0..2 gewählt, Frame-Index), neuer Test `end_painting_frames`: je Variante Standbild + 12 Frames als Ressource vorhanden, gleiche Größe, jeder Animations-Frame 1 weicht vom Standbild nur wenig ab (gleicher Start), jede Animation ändert sichtbar etwas.
5. Runden (A8c): Runde 1 erstellen → Kontaktbogen 4–6x neben Vanilla ansehen → Note → Runde 2/3 nachbessern. Bewertung je Runde unten.
6. Vorschau `/root/sb-tools-b/previews/b-paint12-preview.html` + GIFs in `previews/b-paint12/` (Größe!), Antwortcode PAINT12.

## Entscheidungen
- Ping-pong statt eigener Folge je Animation: keine neue Datenquelle für den Client nötig; Bewegungen sind darauf entworfen (Blinzeln, Flügelschlag, Leuchten, Öffnen …).
- Animations-Zufall auf dem Client (kein Netz), wie bisher.
